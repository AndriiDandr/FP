# Лабораторна робота №4. Рекурсія та мемоізація

**Варіант 4 — рекурсивний пошук у списку.** Рекурсивний бінарний пошук у відсортованій
незмінній послідовності, ітеративна альтернатива, рекурсивні `lower_bound` / `upper_bound`
для дублікатів, мемоізований пошук по `tuple` через `lru_cache`, тести знайдених і відсутніх
значень, порівняння часу з ітеративним і лінійним пошуком.
Плюс базове завдання методички: quicksort, обходи дерева, мемоізований Фібоначчі.

## Цілі

- сформулювати базовий випадок і рекурсивний крок; тримати рекурсивні функції чистими;
- мемоізувати повторні обчислення через `functools.lru_cache` (`cache_info`, `cache_clear`);

## Базовий випадок і рекурсивний крок

- `binary_search(xs, t, lo, hi)`: база — `lo >= hi` (порожній діапазон) → `-1`; `xs[mid] == t` → `mid`;
  крок — пошук у правій `[mid+1, hi)` або лівій `[lo, mid)` половині. Глибина ≈ `log2(n)`.
- `lower_bound` / `upper_bound`: база — `lo >= hi` → `lo`; крок — та сама половинна рекурсія.
- `fib(n)`: база `n < 2`; крок `fib(n-1) + fib(n-2)`.

## Ліміт рекурсії CPython і відсутність TCO

`sys.getrecursionlimit()` за замовчуванням 1000 кадрів; глибша рекурсія дає `RecursionError`.
CPython свідомо не робить tail-call optimization: навіть «хвостовий» виклик
`return binary_search(xs, t, mid + 1, hi)` створює новий кадр стеку. Бінарному пошуку це не
загрожує — для мільйона елементів потрібно лише ~20 кадрів, — але лінійні рекурсії
(`preorder` на виродженому дереві, наївні рекурсії по списку) падають після ~1000 рівнів.
Тому `binary_search_iter`, `bfs_level_order` і `dfs_preorder_iter` безпечніші для довільних
даних, а підняття ліміту через `sys.setrecursionlimit` ризиковане (можливий крах інтерпретатора).

## Порівняння часу (python main.py)

| Обчислення | Час |
|---|---|
| 1000 пошуків у `tuple` з 1 000 000 елементів — рекурсивний | ~1.5 ms |
| те саме — ітеративний | ~1.2 ms |
| те саме — лінійний пошук | ~22 000 ms |
| `fib(30)` з кешем / без кешу | ~0.03 ms / ~70 ms |

Рекурсивна версія трохи повільніша за ітеративну через накладні витрати на кадри стеку,
але обидві мають O(log n) і на порядки швидші за лінійний пошук O(n).
